02 / Architecture
01 · Architecture

One authoritative booking path.

The client chooses. The database decides. Every capacity-changing request passes through the same host lock.

1
React guest/host UIBrowse, hold, confirm, manage
2
Express JSON APIValidate input and auth
3
Postgres transactionIdempotency lock → host row lock
4
Check and writeFresh clock, schedule, occupancy
5
CommitBooking + notification sink

Hold request flow

Require an offset-bearing ISO instant and Idempotency-Key. Resolve the requested host and event. Never trust the client to decide availability.

Confirmation and change

Re-lock the host, verify live state, and commit the booking plus notification in one transaction. Reschedule validates the destination before moving.

Consistency boundary: availability reads, booking writes, and host schedule edits all use the same host row lock. Different hosts proceed independently.

03 / Data model
02 · Data model

Constraints first. Coordination where it belongs.

Postgres stores real instants. Availability remains local-wall-clock based with IANA time zones.

hosts

UUID PK, unique handle, IANA timezone, password hash. Row is the serialization lock for all scheduling changes.

events

Host FK, unique (host, slug), duration 15–120 minutes, capacity 1–100, buffer/notice/horizon checks.

weekly_windows

ISO weekday 1–7, start/end minute values, valid non-overlapping intervals for recurring schedules.

date_overrides

Composite PK (host, date), JSON array replaces weekly hours; empty array means a day off.

bookings

UUID, host/event, status, start/end, buffered busy intervals, expiry, guest details, private manage token.

idempotency_keys

Key PK, fingerprint, booking FK. Same request retry returns the original hold; changed payload is rejected.

notifications

Append-only confirmation, reschedule and cancellation events recorded in the same transaction as booking changes.

sessions

Hashed token PK, host reference, expiration, invalidated at logout and when expired.

Invariant split: keys, foreign keys, uniqueness and checks live in the schema; overlap logic and group capacity are enforced under the locked host row.

04 / Key decisions
03 · Key decisions

Seven deliberate choices that protect correctness.

1

Host-level row lock. Instead of locking events or slots, this covers all event types for the same host and handles multi-seat capacity.

2

Database clock after lock. Expiry is evaluated only after the lock is acquired, so waiting requests use fresh time.

3

Live expiry predicate. Capacity excludes expired holds immediately without a background worker.

4

Idempotency fingerprints. Same key + same normalized payload replays; changed payload fails with 409.

5

Atomic reschedule. One booking moves or fails without partial cancel-then-create behavior.

6

Real UTC instants + local windows. DST gaps and repeats are handled correctly with IANA zones.

7

Transactional notification sink. Confirmation, reschedule, and cancellation are recorded with the booking, not in a separate ad hoc process.

Trade-off

Host serialization is simple and correct, but it can limit throughput for a single very busy host. Measure before changing the design.

05 / Reliability
04 · Reliability

Failure case → behavior → proof.

Contention

40 simultaneous holds yield exactly one winner for capacity 1 or three winners for capacity 3. Test: “40 simultaneous holds”.

Retry / lost response

Same key returns one hold; changed payload fails with 409. Confirmation retries emit one notification. Test: retry assertions.

Expiry during wait

An expired hold can fail confirmation once the lock is released, then allow a new hold. Test: lock-wait expiry check.

Failed move

Destination conflict returns 409 and preserves the original booking. Cancel frees capacity. Test: failed reschedule behavior.

Buffer / cross-event conflicts

Before/after buffers prevent adjacent event overlap. Test: overlapping event types and buffer conflicts.

Bad input / auth / origin

Invalid times, bad zones, unauthenticated host access and hostile origins are rejected. Test: validation and security coverage.

Remaining risk: public hold paths have no distributed bot protection or load benchmark. The login throttle is process-local, not edge-wide.

06 / Time zones
05 · Time zones

Schedule by local clock. Reserve by instant.

How slots are generated

  • Resolve recurring weekly windows and date overrides.
  • Walk real UTC minutes across the host-local day.
  • Test each instant against open availability and busy intervals.
  • Offer quarter-hour local starts when the duration and buffers fit.
  • Return UTC instants and render them in the guest’s selected time zone.

09 / Using AI
08 · Using AI

Accelerated delivery, still checked.

Where it helped

AI helped interpret the assignment, scaffold the TypeScript app, write schema and transaction logic, and generate tests and docs from an empty repo.

Where it helped again

It surfaced concurrency edge cases like lock-wait expiry and DST behavior, which were made explicit in integration tests.

Where it misled

Environment issues—missing PDF library, Docker engine constraints and browser verification limits—were real. The log records the truth and no successful E2E claim is made.

Best practice: use AI to widen the solution space and identify edge cases, then ground claims in source, tests and explicit limitations.

09 · Gaps and next steps

Known gaps

  • No real email delivery, calendar sync or reminders.
  • No waitlist, round-robin routing or production recovery workflow.
  • No distributed anti-abuse protection or public load benchmark.
  • Notification sink is durable intent, not a delivery queue.

Next steps

  • Run guest and host browser flows at desktop/mobile widths.
  • Add Playwright coverage and cold-start deployment checks.
  • Measure throughput under load and tune lock contention.
